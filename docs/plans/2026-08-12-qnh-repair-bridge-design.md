# 牵牛花商品图修复闭环设计

日期：2026-08-12

## 背景

即时零售图片工作台已经具备商品主档补全、23 类目图位配方、7 张基础图、平台特殊图、批量生成、内部质检和平台上传包，但仍停留在“产出图片”的阶段。张家山店实跑的 `qnh-image-pipeline` 已验证了牵牛花商品图修复的关键事实：门店级写图是整列表重推，接口成功回执不等于真实落库，包装保真不能只靠自动规则，且第一次门店级自定义会让图片与租户主档后续更新解耦。

因此，本次将实跑流水线真正整合为“盘点 -> 审核 -> 计划 -> 受控写入 -> 回读”的闭环，同时保持浏览器前端不直接持有牵牛花写权限。

## 目标

- 在应用中提供独立的“商品图修复”工作区。
- 从本机受控执行器读取目标 SPU 的现有主图、详情图和特殊图实况。
- 强制逐张审核现有图集，明确保留或剔除，并记录原因。
- 对新增图片提供源图/成图并排与放大核验，强制人工 `PASS` 或 `REJECT`。
- 只允许已通过审核的图片进入不可变计划包。
- 由绑定 `127.0.0.1` 的本机执行器执行上传和牵牛花写入。
- 写前校验租户、门店和完整图集快照；写后 fresh-fetch 逐项 exact 比对。
- 每笔操作保留快照、台账和断点状态，任一失败立即停批。

## 非目标

- 不让网页直接调用牵牛花写接口。
- 不自动判定包装印刷是否保真，机器规则只提供提示，人负责最终闸门。
- 不生成配料表、营养成分、背标、备案、证书、检测报告、能效或水效材料。
- 不接受命令行临时传入任意 SPU 或图片 URL执行写入。
- 不在第一版支持跨多个租户或多个门店并行写入。

## 架构

采用三层结构：

```text
React 工作台
  商品图集盘点 / 违规图标记 / 保真对比 / PASS-REJECT / 计划摘要
        |
        | HTTP JSON，仅允许 http://127.0.0.1 或 localhost
        v
本机 QNH Bridge
  Origin 校验 / 计划校验 / 落盘 / 执行锁 / 确认短语 / 状态与台账
        |
        v
QNH Pipeline
  CDP 登录态 / 租户门店断言 / 图床上传回读 / 写前快照 / 写后 exact 回读
```

前端只保存桥接地址和不敏感的门店摘要。CDP 端口、登录态和写接口只存在于本机执行器配置中。

## 工作流

### 1. 连接与身份确认

用户打开“商品图修复”，连接默认 `http://127.0.0.1:8768`。Bridge 返回：执行器版本、门店名称、租户 ID、门店 ID、是否已有写入任务。前端不允许连接非回环地址。

### 2. 读取现有图集

用户选择当前商品项目并填写牵牛花 SPU ID。Bridge fresh-fetch 返回：

- 主图列表及顺序
- 详情图列表及顺序
- 特殊图类型、是否必需、当前图片
- `customizedPicFlag` 与 `customizedPicContentFlag`
- 本次读取时间和快照指纹

每张现有图片默认状态为“未审核”，必须逐张改为“保留”或“剔除”。剔除必须选择原因或填写说明。任何未审核图片都会阻断计划生成。

### 3. 新图保真闸门

工作区读取当前项目已完成的 7+1 图片。每张拟写入图片必须绑定一张真实来源图，并展示：

- 左侧真实来源图
- 右侧拟写入图
- 双图独立放大入口
- 包装文字、品牌、规格、颜色、数量和结构核对清单
- `PASS` / `REJECT` 结论与备注

`REJECT` 图片不会进入计划；未审核图片阻断计划。证照、背标和其他真实材料类型只能选择 source-only 输出。

### 4. 不可变计划

前端根据审核结果生成 schema v1 计划，包含：

- 门店与租户身份
- SPU、商品名称、条码、货号
- 写前完整图集快照与指纹
- 每张现有图的保留/剔除决定和原因
- 每张新增图的来源、目标位置、审核结论和图片数据
- 特殊图 `pictureType`
- 门店级图片解耦确认状态

Bridge 对计划规范化并计算服务端 SHA-256，落盘后返回 `planId`、变更摘要和一次性确认短语。计划创建后不再修改；变更必须创建新计划。

### 5. 受控执行

正式执行前，用户必须确认：门店名称、商品数、新增图数、剔除图数、特殊图数，以及“门店级图片将与租户主档后续图片更新解耦”。前端提交服务端确认短语。

Bridge 使用文件锁保证同一门店同一时间只有一个写任务，执行顺序为：

1. fresh-fetch 并与计划里的完整图集快照 exact 比对。
2. 保存写前快照。
3. 上传新增图片，并从图床 GET 回来比对字节长度。
4. 主图、详情图、特殊图依次写入。
5. 每一类写完立即 fresh-fetch，逐项 exact 比对。
6. 写台账并更新断点；任何失败立即停止。

修复草稿随零售项目持久化。库存重新读取后，如果指纹变化，清空旧的剔除决定、计划 ID 和执行状态，避免沿用过期审核。

## Bridge API

所有响应为 JSON，CORS 只允许本地开发源，服务仅绑定 `127.0.0.1`。

- `GET /v1/health`：门店身份、版本和忙碌状态。
- `POST /v1/inventory`：按计划中的单个数字 SPU 读取现有图集。
- `POST /v1/plans`：校验、规范化并落盘不可变计划和图片资产。
- `GET /v1/plans/<planId>`：读取计划摘要、状态和最近台账。
- `POST /v1/plans/<planId>/execute`：提交确认短语并执行。

Bridge 不提供任意脚本执行、任意 URL 上传或任意接口透传能力。

## 安全规则

1. Bridge 配置缺少门店、租户或 CDP 参数时拒绝启动。
2. 计划门店身份必须与 Bridge 配置完全一致。
3. SPU 必须是数字字符串；图片必须是受限 MIME 的 data URL，单张不得超过平台上限。
4. 现有主图和详情图必须全部审核，剔除必须有原因。
5. 新增图必须 `PASS`，且来源图与成图不能是同一图片 ID。
6. `authentic_document` 和 `back_label` 不得来自 AI 处理模式。
7. 完整图集快照与执行时实况不一致则拒绝执行。
8. 未确认门店级解耦则拒绝执行。
9. 同店执行使用独占文件锁；失败后不继续后续商品。
10. 每次上传、写入、回读与失败均写 JSONL 台账。

## UI

顶部新增“商品图修复”入口，使用独立工作区而非继续加高普通出图侧栏。桌面端采用左中右三栏：

- 左栏：Bridge 连接、当前商品、SPU、门店身份。
- 中栏：现有图集审核、新图源成对比与放大。
- 右栏：闸门进度、变更摘要、生成计划、执行确认和台账。

移动端使用“连接 / 图集 / 对比 / 执行”四个标签，底部固定区只保留当前阶段的主命令。不会在卡片内嵌套卡片，也不会把内部审核文字写入商品图片。

## 错误处理

- Bridge 未启动：显示启动命令和连接失败原因，普通出图功能不受影响。
- 登录态失效：执行器返回明确的 QNH 鉴权错误，不自动切换门店或重试写入。
- 图集变化：标记计划过期，要求重新读取和审核。
- 上传回读失败：停止，不进入任何写入。
- 写后回读不一致：停止并保留前后快照，提示人工检查；不把接口 `code:0` 当成功。
- 并发执行：返回 409 和当前任务摘要。

## 测试

- TypeScript 单元测试覆盖桥接 URL、安全计划生成、审核完整性、特殊图类型和过期计划。
- Python 单元测试覆盖计划 schema、身份校验、图片限制、确认短语、执行锁和状态机。
- 使用 fake QNH adapter 做 Bridge HTTP 冒烟测试，不依赖真实门店登录态。
- 浏览器验证桌面和 390px 移动端的连接失败、库存审核、对比、计划摘要和执行确认状态。
- 真实牵牛花写入不在自动测试中执行，只通过现有张家山已跑通计划格式和只读 inventory 进行兼容验证。

## 验收标准

1. 网页无法直接调用牵牛花写接口，只能访问回环 Bridge。
2. 任一现有图片未审核时不能生成计划。
3. 任一拟新增图片未 `PASS` 时不能进入计划。
4. 计划创建后，执行前图集发生变化会被 Bridge 拒绝。
5. 未确认门店级图片解耦不能执行。
6. 写后必须以 fresh-fetch exact 比对作为成功依据。
7. 任一失败立即停批，并在台账中可定位。
8. 普通 7+1 出图、批量商品、条码主档和平台上传包保持兼容。
